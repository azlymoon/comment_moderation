# Метрики кода: запуск и улучшения

Этот проект содержит конфигурацию и сценарии для расчёта метрик качества кода на Python.
Ниже описано, как запускать метрики, какие показатели используются и какие изменения
внесены для их улучшения.

## Как запустить

1. Установите инструменты (внутри вашего виртуального окружения):
   ```bash
   pip install radon xenon pylint
   ```
2. Сводный запуск и HTML‑отчёт:
   ```bash
   make metrics-html
   # Откройте reports/index.html в браузере
   ```
3. Для JSON‑отчётов без HTML:
   ```bash
   make metrics-json
   # отчёты появятся в каталоге reports/
   ```

## Что считается

- Cyclomatic Complexity (radon cc)
  - Показывает число независимых путей в функции/методе.
  - Чем меньше — тем проще поддерживать. Шкала A (лучше) … F (хуже).
- Maintainability Index (radon mi)
  - Показатель сопровождаемости файла: выше — лучше. Целевое значение > 65.
- Halstead Metrics (radon hal)
  - Volume/Difficulty/Effort — косвенно отражают информационный объём и когнитивную сложность.
- Pylint (качество дизайна и сцепление)
  - Сводка F/E/W/R/C и отдельные показатели: `too-many-ancestors`, `cyclic-import`, `too-many-imports`.
- Xenon (порог‑контроль сложности)
  - Опционально “заваливает” сборку, если сложность превышает пороги (см. `setup.cfg`).

## Пороговые значения

- CC: целевое A (≤ 5), абсолютный максимум B (≤ 10).
- MI: целевое > 65 (приоритет на повышение для файлов ниже 50).
- Halstead: снижение объёма и трудности у “лидеров”.
- Pylint: критических/ошибок — 0; снизить предупреждения по сцеплению/наследованию.

## Внесённые улучшения

1. Снижение цикломатической сложности в `app/core/store.py`:
   - Разбили крупные функции на помощники:
     - `validate_api_key()` → `_fetch_active_keys_by_prefix()`, `_is_key_valid()`, `_get_active_service()`
     - `authenticate_admin()` → `_get_valid_admin_session()`, `_get_active_admin_user()`, `_check_roles()`
     - `ensure_demo_data()` → `_ensure_admin()`, `_ensure_service()`, `_ensure_api_key()`, `_ensure_toxic_category_and_rule()`
   - `compute_statistics()` переписан на агрегирующие SQL‑запросы вместо ручных проходов списков.
   Ожидаемый эффект: функции переходят в CC‑ранг A, MI файла растёт, Halstead объём падает.

2. Устранение замечаний Pylint по инфраструктуре БД:
   - Переписан `app/db/session.py` без `global`, введён класс `DB` с полями `engine` и `session_factory`.
   - Переименована фабрика сессий на `session_factory` (snake_case), сохранён публичный API `get_session()`.

3. Исправление конфигурации линтера:
   - Убраны устаревшие опции из `.pylintrc` (например, `max-imports`, `R0905`).

4. Валидация настроек:
   - `app/config.py` — добавлен `@classmethod` к валидатору `validate_dsn`, чтобы подавить ложноположительное предупреждение `no-self-argument` и сохранить совместимость с pydantic v2.

## Что делать дальше

- Пройтись по файлам с низким MI (см. reports/index.html) и провести точечный рефакторинг:
  - Декомпозиция длинных функций.
  - Упрощение ветвления и ранние возвраты (guard clauses).
  - Вынос часто повторяющейся логики в отдельные помощники/репозитории.
- Включить проверку метрик в CI (GitHub Actions) и публиковать артефакты `reports/`.
- Дополнительно подключить `mypy` и `ruff` для статического анализа.
